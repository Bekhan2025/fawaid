# Интеграция с текущей читалкой

## Что читать перед правками

| Путь | Что выяснить |
|---|---|
| `src/lib/types.ts` | Реальные варианты `Section`, `Chapter`, `Section.atlas`; поля, которые поддерживаются |
| `src/content/book.ts` | Сборку `BOOK`, `BOOK_TEXT`, `BOOK_ENTRIES_ORDERED`, подключение глав и словаря |
| `src/content/chapter-links.json` | Единственный актуальный источник привязок `entryId → chapterId` |
| `src/components/reader/blocks.tsx` | Порядок и видимость секций, маркировку дополнений, поведение отсутствующего слоя |
| `src/components/reader/atlas.tsx` | Поддерживаемые визуальные примитивы, общий диспетчер |
| `src/components/reader/inline.tsx` | Поддержку `**…**`, `[[term:id]]`; обычные строки могут не поддерживать их |
| `src/components/reader/reader-app.tsx` | Выбор главы по активной записи, переключение слоёв, URL и прогресс |
| `src/app/globals.css`, `src/components/ui/` | Токены и готовые поведенческие примитивы |
| `scripts/validate-content.ts`, `tests/e2e/`, `package.json` | Фактические проверки и команды |

Не считай описания в документации доказательством реализации: проверь код.

## Замороженный текст и привязка — разные данные

JSON `book-text` и оглавление сохраняются побайтово. Новые главы не требуют PDF.
Исторический `chapterId` внутри них нельзя обновлять или считать актуальнее карты привязок.

**Известное переходное состояние:** ранняя версия `book.ts` импортирует эти значения
напрямую, а валидатор требует совпадения карты с замороженными файлами. Создание
новой привязки при такой сборке потребует небольшой адаптации приложения, а не регенерации.

При задаче реализации новой главы, если это состояние ещё сохраняется:

1. Наложи карту привязок на импортированные записи **при сборке данных**, создавая новые
   объекты. Нормализуй и `BOOK.parts`, и `BOOK_TEXT`/`BOOK_ENTRIES_ORDERED` одинаково.
2. У отсутствующей в карте записи эффективный `chapterId` отсутствует/равен `null`
   согласно типу. Не возвращай устаревшую привязку из сырого JSON через fallback.
3. Все потребители (сайдбар, выбор главы, поиск, навигация) используют эту согласованную сборку.
   Не мутируй импортированный JSON или исходный `TOC_PARTS` на месте.
4. Валидатор проверяет **эффективные** привязки, наличие записи и главы в карте,
   уникальность и остальные инварианты. Не отключай проверку привязок ради зелёного результата.
5. Адресно проверь: новая привязка работает без записи в исходных файлах;
   удаление/переназначение карты не воскрешает исторический `chapterId`;
   входные объекты и их файлы не изменились; неизвестная запись/глава отвергается.

Это условная адаптация для создания глав, не требование переписывать приложение
при каждом запуске скилла. При запросе одной концепции достаточно указать нужную интеграцию.

## Подключение главы

- Выбери свободные `chapterId`/`num` по фактическим данным; не выводи их из номера страницы.
- Помести данные в `src/content/chapters/<chapterId>.ts`, экспорт с типом `Chapter`.
  Импортируй в `book.ts`, добавь в `BOOK.chapters`, затем в карту привязок.
- Используй стабильные ID секций с понятным префиксом, чтобы DOM-якоря не конфликтовали.
  Не меняй `entryId`, порядок чтения, заголовок и страницы исходной записи.
- `Section.book` — устаревшее поле адаптированного пересказа. Не используй его как слой книги
  и не копируй в него исходный текст. Новая глава содержит Разбор/Атлас.
- Не меняй глобальное определение термина ради одной главы без проверки других употреблений.
  Если контекстное значение другое, используй локальное пояснение или отдельный обоснованный термин.

## Текущие формы и их семантика

`mini`/`spectrum` — шкалы, `examples` — фиксированная модель минус/середина/плюс,
`steps` — последовательные шаги, `cards` — карта содержания, `chain` — причинная связь.
Совпадение удобных полей не означает совпадение смысла. Не помещай перечень последствий
в `steps` только потому, что он принимает `title` и `text`.

`razbor` сейчас поддерживает `keyIdea`, `paragraphs`, `list`. Более сложная форма
(например, ветви аргумента или пары вопросов и ответов) может потребовать расширения.
Не записывай интерактивную разметку строкой HTML и не внедряй произвольный JSX в книжный JSON.

## Если существующих типов недостаточно

Минимальное расширение затрагивает типизированные данные и соответствующий рендерер.
Для нескольких принципиально разных схем выбирай разные discriminated union-варианты;
не превращай `cards` в неограниченный мешок опций, меняющий смысл от главы к главе.
Общую отрисовку можно переиспользовать, сохраняя различимые данные отношений.

Текст с `[[term:id]]` и `**…**` пропускай через `renderInline` там, где он поддерживается,
либо используй обычный текст. Проверяй **фактический** рендеринг новых заголовков,
caption, карточек и lead: наличие разметки в данных не гарантирует её отображения.

Если слои требуют разной структуры, поддержи явную видимость/раздельные данные секций
и фильтрацию до вывода заголовка. Секции другого слоя не должны оставлять пустые заголовки
или заглушки в готовом результате. Сохрани работу существующих глав, не мигрируй все 136 записей.

Для новой интерактивности используй подходящий shadcn-примитив, когда он есть.
Для статичных отношений достаточно семантического HTML/CSS/SVG. Объём новой абстракции
должен объясняться текущей задачей, а не гипотетическими будущими разделами.

## Открытие и проверки

Прямые ссылки: `/?entry=eID&layer=book|razbor|atlas`. Переход к исходному абзацу:
`/?entry=eID&layer=book#eID-para-N` (индекс с нуля). Не придумывай схему URL заново.
Проверь актуальную поддержку якорей и фокуса в `use-reading-location.ts`.

При правках только данных сначала `bun run check`, затем реальные клики по новой главе.
При правках типов/рендереров также проверь затронутые готовые главы и сборку;
`bun run release:check` уже объединяет проверки, сборку, отчёт JS и e2e — не повторяй их
отдельно после успешного полного цикла без новой причины. Нужен установленный Chromium;
сборка может потребовать доступ к Google Fonts. Не запускай dev и build одновременно в `.next`.
